# Контрибьюция

> Если хочешь вносить изменения в этот проект - прочитай этот файл полностью. Дважды. Если будешь соблюдать эти правила - твой PR будет принят без проблем.

## Общие правила

1. **Код должен быть рабочим.** Перед отправкой PR запусти проект, протестируй свою фичу, убедись что всё работает. Неработающий код я не буду рефакторить за тебя.
2. **Стиль кода должен совпадать с исходной кодовой базой.** Это значит:
   - Строгая типизация там, где это предусмотрено языком/проектом.
   - Везде, где проект использует асинхронность - async/await.
   - Централизованное логирование через общий логгер. Используй существующий формат и уровни.
   - Кастомные исключения/ошибки вместо голых `Exception`. Оборачивай внешние вызовы в retry с экспоненциальным backoff.
   - Конфиг выноси в единый класс/модуль и читай из переменных окружения или конфиг-файлов с fallback-значениями. Не хардкоди параметры.
   - Для ввода-вывода используй асинхронные/не blocking-инструменты. Для файлов и БД - соответствующие асинхронные драйверы.
   - Для форматирования выводов используй общие вспомогательные функции проекта.
   - Именование: `snake_case` для функций/переменных, `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант (всё по стандарту в общем).
3. **Коммиты.** Пиши осмысленные сообщения. Если коммит решает несколько задач - разбей на несколько. Не коммить секреты, конфиги с ключами, кэш, логи.
4. **Зависимости.** Если хочешь добавить новую библиотеку - сначала обсуди в Issues или в телеграм. Обоснуй, почему она нужна и почему нельзя обойтись без неё.
5. **Тестирование.** Перед PR убедись, что:
   - Проект запускается без ошибок
   - Основные сценарии работают
   - Нет падений при невалидных/пустых данных
   - Логи выводятся корректно и без секретов
   - Если меняешь схему хранения - проверь миграции/совместимость
   - Если добавляешь пользовательские строки - не забудь про локализацию, если проект многоязычный

## Структура проекта

Структура зависит от конкретного репозитория. Прежде чем вносить изменения, изучи текущую архитектуру и следуй ей. Не выдумывай новую структуру модулей без обсуждения.

Правила универсальны для всех проектов экосистемы:

- Всю конфигурацию храни вне кода (`.env`, конфиг-файлы).
- Бинарники, сессии, кэш, данные, секреты, логи - в `.gitignore`.
- Лицензия - MIT, если не оговорено иное.
- Универсальные утилиты (клавиатуры, форматирование, загрузка языков, retry) - используй существующие, не пиши дубликаты.

## Что можно менять, а что нет

### Можно (согласуй в Issues или лично)

- Добавление новых фич, не ломающих существующую логику
- Исправление багов
- Улучшение механизмов отказоустойчивости, antiflood, кэширования
- Оптимизация производительности
- Добавление новых языковых пакетов или исправление переводов
- Обновление зависимостей (с обоснованием)

### Нельзя

- Ломать обратную совместимость без обсуждения
- Удалять или переименовывать существующие переменные окружения / конфиг-параметры
- Изменять схему БД без миграции
- Убирать типизацию или async/await там, где они используются
- Коммитить секреты, сессии, логи, личные данные и т.п.

## Процесс разработки

1. Создай Issue с описанием задачи (если это новая фича или крупное изменение).
2. Обсуди реализацию.
3. Форкни/веткани и делай коммиты.
4. Отправь PR, следуя шаблону.
